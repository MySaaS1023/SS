# Administrator invitation candidate — disabled locally and in production

This is an implemented, mock-tested release candidate, not an activated invitation service. No invitation has been prepared in production, no Auth user has been created, no email has been sent and no administrator access has been granted by this work. The named administrator requested by the owner must be entered into the protected form only after role, scope and workflow approval; no recipient identity is hardcoded into source or fixtures.

## Workflow

1. An active Super Admin opens `/admin/settings/admins`. The management loader and every invitation operation use the existing membership-backed `getAdministratorManagementContext`. Ordinary administrators, partners and customers receive no recipient details or management capability.
2. Prepare a proposal with a name, email and fixed **Admin** role. The proposal is saved and audited without an Auth call, delivery or membership. Preview lists Referral Program, Client Scheduling, Client Handoff and QR Code; it explicitly excludes administrator/security management.
3. After independent owner approval, type the exact recipient email, check the approval confirmation, select Send, then confirm the final dialog. A guarded database transaction reserves exactly one send attempt and stores a SHA-256 fingerprint of a cryptographically random 32-byte nonce. Duplicate or concurrent sends cannot reserve another attempt.
4. The existing Supabase Auth `admin.generateLink({ type: "invite" })` generates the invitation without sending an Auth email. **This operation can create a new, unconfirmed Auth identity even if the later general Resend call fails.** The UUID, normalized email, unconfirmed state and creation time are checked and bound to the proposal before delivery. No existing Auth identity, partner or membership is repurposed, updated or overwritten. Existing-user onboarding is deliberately refused and requires a separately approved flow.
5. The existing general `RESEND_API_KEY` and configured `RESEND_FROM_EMAIL` (or existing general-purpose approved `HANDOFF_FROM_EMAIL`) send the invitation with a durable per-invitation idempotency key. No referral API key or referral sender is read. The invitation callback URL contains a random invitation UUID, nonce and Auth invite token hash, without recipient contact data. Raw nonce and Auth token are never stored in the invitation table or returned to the administrator form.
6. Only a provider-returned message UUID records `sent` / **accepted by Resend**. This is not inbox delivery and does not activate membership. Rejected, indeterminate and audit-failure outcomes remain blocked from automatic retries. Unknown outcomes require owner/provider reconciliation before revoking/reissuing anything; never blindly regenerate a link or send another email.
7. `/auth/admin-invite` accepts only the `invite` proof type and checks nonce, hashed Auth token fingerprint, pending sent state, expiry and server-bound UUID before using Supabase `verifyOtp`. An existing session belonging to another person is left untouched and refused. The callback re-verifies the resulting Auth user and redirects to a clean URL, retaining the nonce in a Secure (production), HttpOnly, SameSite cookie for at most 15 minutes.
8. The recipient reviews the fixed role/scope, creates and confirms their own password (12–256 characters) and explicitly accepts. A same-origin, bounded, rate-limited POST requires the recipient's independently verified Supabase session plus the invitation nonce. A transaction claims acceptance before password mutation to block concurrent/replayed password changes. After the password write, another transaction rechecks active inviter, exact verified email/UUID, nonce, role, expiry and claim; it inserts the **Admin** membership, consumes the invitation and writes the audit event atomically. It can never grant Super Admin. The invitation session closes and the recipient signs in through the existing admin login.
9. Revocation requires exact recipient confirmation, an active Super Admin, a guarded RPC and an audit event. Revoked, expired and accepted links cannot activate access. Revoking an invitation does not delete an Auth identity or an accepted membership; existing administrator management handles an accepted member's role/status. Failed acceptance after an atomic claim requires owner review and cannot be automatically retried.

## Required approval and setup before activation

- Review/apply the existing administrator management migration, bootstrap the immutable verified owner Auth UUID and audit that bootstrap in a separately approved transaction. Verify membership-backed authorization and last-active-Super-Admin protection before any cutover.
- Review/apply `supabase/migrations/202611130002_admin_invitation_workflow.sql` only after database preflight and backup approval. It adds invitation columns and seven service-role-only guarded RPCs. Browser `anon`/`authenticated` roles receive no table or RPC privileges; service role receives table SELECT only and guarded RPC execution. It does not alter business records, payments, referrals, customers, handoffs or existing Auth users.
- Run real isolated database checks for SQL compatibility, RLS/grants, double-send contention, revoke/accept races, callback replay, mismatched account/email, expiry and durable audit atomicity. These SQL/RLS/concurrency behaviors have **not** been live verified in this environment; pure fixtures and static migration checks are not a substitute.
- Validate the existing general Resend key, verified sender and actual API acceptance independently. The previously reported general `400 validation_error` is a separate unresolved blocker; this candidate neither changes credentials nor bypasses that issue with referral credentials.
- Verify the existing Supabase Auth invite flow and allowed redirect configuration for the deployed callback. Default Auth invitation lifetime must permit the intended one-hour link; the database imposes its own one-hour maximum regardless. Review any required redirect allowlist change with the owner; no settings are changed by this implementation.
- Review email scanning behavior: visiting the callback exchanges the one-use Auth invite proof, while membership still requires explicit acceptance and password entry. Security scanners may consume the Auth proof prematurely. Verify the actual mailbox/provider behavior in an owner-approved synthetic test; add a user-initiated verification interstitial before activation if required. Never claim acceptance/inbox receipt solely from rendering an email preview.
- After all checks and explicit owner approval, enable **both** `ADMIN_MANAGEMENT_ENABLED=true` and **`ADMIN_INVITATIONS_ENABLED=true`** in the approved environment and release. Both remain unset/false now. Existing authentication and general/referral email configuration remain unchanged while gates are off.
- Obtain final approval for the exact recipient, **Admin** role and four-workspace scope before preparing/sending the real invitation. Do not send it as part of QA. Use only synthetic addresses and mocked providers until a controlled real test is authorized.

## Local verification and limits

`tests/admin-invitations.test.ts` exercises input/role restrictions, redacted preview, cryptographic nonces, concurrent delivery claims, no automatic send on preview, provider acceptance/rejection/unknown outcomes, retry blocking, identity/token/nonce/expiry mismatches, one-time acceptance claims, revoked-in-flight refusal and failed-password behavior with injected fixtures only. No test calls Resend or Supabase Auth. The route wrappers add origin checks, a 4 KiB streaming JSON limit and process-local rate limiting; the database claims provide durable send/accept replay protection across instances. Deployments with high abuse exposure should verify the existing shared edge throttling policy rather than treating process-local limits as a global limiter.

Never log invitation query parameters, cookie contents, Auth tokens, generated invitation URLs or API keys. Invitation routes must retain private/no-store/no-referrer/noindex headers and stay excluded from referral/activity tracking. Rollback is to keep the gates off; do not remove an accepted membership outside the separately approved, audited administrator-management workflow.
