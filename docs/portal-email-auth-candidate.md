# Final cleanup: secure email-link authentication candidate

`PORTAL_EMAIL_LINK_ENABLED` is **unset/OFF**. This phase uses **mocks only**. No real email, account creation, Auth metadata change, production configuration, invitation, migration or deployment is performed by this implementation. The existing password and forgot-password interfaces stay available. Do not describe this candidate as verified in production.

## Provider and delivery audit

Authentication uses the existing **Supabase Auth** provider through `signInWithOtp`, not general or referral Resend credentials. The live read-only audit found that Supabase is using its built-in email service, which is rate-limited and explicitly not intended for production apps; custom SMTP is not configured. Consequently, neither production sender readiness nor actual email delivery is verified. The prior general Resend `400 validation_error` is a separate unresolved issue and is not repaired by this login UI. Do not change either referral credential.

## Request, confirmation, and authorization

- Both portals gain a gated email form and dedicated `/api/admin/auth/email-link` or `/api/partner/auth/email-link` endpoint. The response, status and cookie behavior are generic for unknown addresses, wrong roles, rate limits, ineligible users and provider failures. Directory/provider work is deferred with existing Next `after()`, outside the response timing; body size, origin and media type are checked.
- Admin eligibility reuses active UUID-bound memberships when enabled; until that separate transition, it reuses the existing administrator allowlist and a bounded, server-only existing Auth directory lookup. No directory rows are logged or exposed. Partners require their current approved UUID-linked record and an exact matching confirmed Auth email. Only existing confirmed, eligible identities can reach `signInWithOtp`; `shouldCreateUser: false` prevents automatic signup/approval.
- Supabase must issue an actual one-time **magiclink** token. Recovery, invitation, ordinary sessions, Representative IDs and user-supplied emails cannot prove login. Current role and approved partner contact are checked again after provider verification, before a fixed portal destination is selected. A partner token cannot grant administrator permissions.
- `/auth/email-access` is a standalone Route Handler document, without the application layout, referral tracker, scripts or external assets. GET never exchanges a provider token: scanners can follow it without creating a session. A valid hash moves into a five-minute HttpOnly, Secure-in-production, SameSite=Lax, path-restricted cookie and redirects to a clean confirmation URL. The confirmation HTML never contains the hash and uses private/no-store, no-referrer, noindex/nofollow and restrictive CSP headers.
- Only an explicit same-origin POST on that clean confirmation page exchanges the cookie token using `verifyOtp({token_hash, type: "magiclink"})`. The provider enforces expiration and atomic single use, including concurrent requests; cookie deletion alone is not replay protection. The return destination is independently restricted to the selected portal and its existing forced-password setup screen. All failures use fixed generic login URLs; `next`, host manipulation and foreign return URLs are not honored.
- An already verified authenticated account is never silently replaced or signed out by an incoming link. Such an exchange is refused before `verifyOtp`; the existing session is preserved. To switch accounts, explicitly use the existing Sign Out flow first. Invalid/disabled/wrong-type requests do not touch existing sessions.
- Existing `must_change_password` restrictions are retained. This code does not silently clear account setup flags or write Auth metadata. A partner/admin still subject to forced setup is not claimed to have completed a fully passwordless transition. That owner-approved transition must be resolved separately while preserving account access.
- Login requests use in-process IP and hashed per-portal email limits plus existing provider limits. These application limits are **not distributed** across Vercel instances. Durable shared abuse controls or verified provider/WAF enforcement remain an activation requirement.

SMTP setup must not overwrite referral email variables or silently repurpose credentials.
3. Review the exact Supabase Magic Link template for all existing consumers, including the separate Representative-ID candidate. A proposed expression for the new flow is `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=magiclink`, where `.RedirectTo` is the canonical `/auth/email-access?portal=admin` or `?portal=partner`. Existing `/auth/partner-access` has no query string; its current candidate requires compatible template branching or coordinated redirect changes before both flows can be activated together. Do not change templates or enable half-configured routes.
4. Configure a short provider OTP lifetime, proposed **600 seconds or less**, and verify actual single-use/expired/invalid/replayed/concurrent behavior. The application's five-minute confirmation cookie is an additional limit, not proof that Supabase's provider token TTL is already short. Token URLs must be redacted from access/error logging; this code never logs token values, but platform request-URL log settings must be reviewed.
5. Review exact canonical Site URL/redirect allowlist, no broad wildcard/open redirect. Confirm bare route/no third-party tracking and token-free confirmation document. Verify provider failure cleanup, active-session preservation, admin/partner cross-role denial and unchanged legacy fallback with synthetic accounts and an explicitly authorized inbox.
6. Only after approval and these real checks, enable `PORTAL_EMAIL_LINK_ENABLED=true`. The existing `PARTNER_PASSWORDLESS_ENABLED`, `AUTH_RECOVERY_V2_ENABLED` and admin-management flags are independent and remain OFF unless separately approved. Do not remove the fallback/reset screens in the same unverified activation.
