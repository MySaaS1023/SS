# Referral archival candidate — owner approval required

The existing system has no partner draft/save-unsent workflow. Submitted referrals immediately create lead/invitation activity. `partial` is customer intake progress. No partner Delete button or mutation privilege is introduced for those records. Existing customers, attribution, payments, handoffs and financial history remain intact.

The candidate migration `202611120002_referral_record_archival.sql` adds separate archival metadata and transactional audit only. It does not delete or update existing business rows, change existing policies, regenerate IDs, or archive any record on installation. Browser roles have no grants/policies. Even service-role direct writes are revoked; only the guarded RPC can write metadata and audit together.

The API and controls remain unavailable unless `ADMIN_MANAGEMENT_ENABLED=true`, which must remain unset until the administrator migration, owner UUID bootstrap, auth integration and live SQL security verification are explicitly approved. Active Admin/Super Admin membership, same-origin request, exact record confirmation and database dependency checks are required. Rejected unlinked applications, inactive partners with no referral/financial/attribution dependencies, and closed referrals without customer/invitation/financial/handoff/consultation dependencies may be archived. No permanent deletion is available. Archived records stay visible in historical management lists with an archived label; attribution and financial displays are unaffected. Existing audited resource unpublish remains the removal mechanism for resources.

Local tests cover request validation and refusal to invent partner draft eligibility. They do not establish PostgreSQL/RLS execution or concurrency safety. Before activation, execute migration preflight against the approved existing schema; confirm `hire_us_submissions`, all customer invite fields and dependency tables exist; run transactional tests of eligible and ineligible synthetic rows, concurrent dependency insertion, cross-user requests, duplicate confirmation, mandatory audit rollback, direct browser/service-role table write denial and active/disabled membership checks. Verify record metadata immediately refreshes and survives reload. No production migration or destructive QA is authorized by the current UI release.

Owner approval is separately required for both candidate migrations, immutable owner UUID bootstrap, feature activation, invitation sending and any production archival action. The proposed administrator invitation must remain a proposal until explicitly approved. No real messages should be sent during verification.
