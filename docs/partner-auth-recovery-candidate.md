# Authentication candidate — no production cutover

Both server-only gates are **unset/OFF**: `AUTH_RECOVERY_V2_ENABLED`, `PARTNER_PASSWORDLESS_ENABLED`. Existing password login, sessions, callbacks, recovery requests and forms retain their current behavior until an explicitly approved transition. No production Auth settings, credentials, messages, accounts or database records were changed. General Resend's prior `400 validation_error` remains a separate unresolved issue; neither referral nor general Resend credentials are changed or bypassed.

## Audit and recovery fix

The existing shared callback sends partners to `/partner` regardless of a reset request. Existing reset forms treat any ordinary authenticated session as a recovery session, and old reset endpoints do not require separate one-time recovery proof. They redirect to dashboards after password changes rather than completing recovery and returning to login.

The disabled V2 candidate accepts only a Supabase `token_hash` explicitly verified as `type: recovery` at `/auth/recovery`. PKCE login codes, ordinary sessions and magic links cannot mint recovery grants. A random HttpOnly, Secure-in-production, SameSite=Lax cookie is bound to the verified Auth UUID, stable session fingerprint, portal and ten-minute lifetime. Only SHA-256 hashes are stored in the new database table. The reset endpoint atomically consumes the grant before updating the password; consumed, expired, mismatched, manipulated and replayed grants are denied. Failed provider writes require a new recovery link and do not report completion. Password update and confirmation enforce 12–256 characters. A successful update requires provider-confirmed global signout, clears the recovery cookie, displays success and offers login; no automatic dashboard redirect occurs. If signout cannot be confirmed, success is not claimed. Already-issued access JWTs may remain valid until their provider expiry even after refresh-session revocation; do not claim instantaneous invalidation of all access JWTs.

New table/RPC migration: `202611130001_auth_recovery_grants.sql`. It is additive, has no bootstrap/data changes, enables RLS and revokes browser roles' table/function privileges. Service role has SELECT plus specific issue/consume RPC execution only. Consumption is a single conditional UPDATE. **SQL execution, real Auth delivery, actual RLS and database concurrency have not been verified.** Tests use isolated synthetic provider/store fixtures.

## Representative ID passwordless candidate

Existing stable `SS-XXXXXX` representative codes are lookup identifiers, never credentials. The new request endpoint returns the same generic response for unknown IDs, disabled/suspended users, unavailable configuration, rate limits and provider failures; it exposes no email, phone, UUID or provider response. It schedules lookup/provider work using existing Next.js `after()` so their latency is not included in the unauthenticated response. A stateless anonymous Supabase client avoids eligibility-dependent PKCE cookies. Only approved partners with the exact existing Auth UUID, a confirmed existing Auth email matching the partner record, and no protected administrator identity can receive an Auth magic link. `shouldCreateUser: false` prohibits new accounts. Verification at `/auth/partner-access` requires a one-time `magiclink` token hash, confirms current approved partner ownership/contact again, then completes the legacy temporary-password setup flag. This last step is an Auth metadata change and occurs only after approved enablement and successful provider verification. Existing email/password login remains available, and existing sessions are not bulk replaced.

IP and hashed-ID limits reuse the application's in-process limiter; Supabase adds provider limits. The in-process limiter is **not distributed** across Vercel instances. Production enablement requires an approved shared/durable limiter or verified provider/WAF enforcement adequate for ID-targeted harassment. No new paid service has been added. Forgotten IDs or lost contact methods require support identity verification; there is no unauthenticated contact-change endpoint. Contact changes must verify the owner of the account and new email in existing Supabase Auth before updating the partner contact, with appropriate audit and approval. The current candidate deliberately does not implement a new contact-change workflow.

## Owner approval and setup requirements

1. Verify a safe isolated Supabase database/Auth environment or approved synthetic test strategy; inspect existing production catalog read-only. Review/apply the recovery-grant migration **only after explicit owner approval**, then verify actual table/RPC permissions, RLS, expiration, concurrent consume and provider failure behavior before cutover.
2. Inspect existing Supabase Site URL, redirect allowlist, recovery/magic-link templates, SMTP/sending identity and rate limits without exposing credentials. Do not overwrite production settings. Required canonical Site URL: `https://www.steadystartco.com`.
3. Prepare a **Recovery** email template with separate admin and partner destinations. A proposed link expression is `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=recovery`, where the request sets `.RedirectTo` to `https://www.steadystartco.com/auth/recovery?portal=admin` or `?portal=partner`. Review the exact rendered provider template before approval. Existing recovery behavior is not changed until the template and `AUTH_RECOVERY_V2_ENABLED=true` are approved together. A regular default PKCE callback cannot prove recovery and is intentionally refused by V2.
4. Prepare the **Magic Link** template to the exact `https://www.steadystartco.com/auth/partner-access?token_hash={{ .TokenHash }}&type=magiclink` route. Preserve unrelated signup/invitation templates. Approve `PARTNER_PASSWORDLESS_ENABLED=true` only after existing verified provider sending, redirect allowlist and durable abuse controls are proven. Do not enable a half-configured flow.
5. Add only the approved exact redirect URLs to the existing Auth allowlist as necessary (including both `/auth/recovery?portal=...` and `/auth/partner-access`); no broad wildcard/open redirect is required. Confirm templates cannot route to attacker-controlled hosts. Verify valid, expired, invalid, reused, wrong-type and wrong-role tokens with synthetic accounts. Never paste tokens, Auth URLs or codes into logs/chat.
6. Obtain explicit owner approval of the authentication cutover, rollback and existing-partner transition plan. Preserve existing password login and authorized admin access during rollout. Initial tests must use an approved synthetic recipient; no real customer messages are authorized by this task. If provider delivery/redirect/template/database validation is unavailable, leave both gates OFF and report the blocker rather than substitute production credentials.

Administrator invitations remain a separate disabled candidate. Invitation issuance/acceptance and role activation require their own reviewed workflow and owner approval; no administrator invitation is sent by these authentication changes.
